# M05-002 Broader viewport, keyboard, motion, and contrast matrix

## Scope

This increment closes the matrix M05-001 left open: the supported viewport set,
keyboard-only traversal, reduced motion, and contrast. It does not claim a WCAG
conformance statement, screen-reader behavior, multi-browser coverage, or
operating-system text scaling.

## Defects found and corrected

### 1. Tab was bound to the help overlay, so keyboard play was impossible

`toggle_legend` claimed `KEY_TAB` alongside `KEY_F1`. The first Tab opened the
help overlay and focused its close button; every later Tab toggled the overlay
again. No tactical control could ever receive focus, so M05-001's focus outlines
were unreachable in practice.

Tab is now reserved for focus traversal, `toggle_legend` keeps `F1`, and a
deterministic check fails if any gameplay action ever claims Tab again.

### 2. Keyboard users had no entry point

Godot advances GUI focus only from a control that already holds focus. With the
canvas focused and nothing selected, Tab did nothing. The first Tab or Shift+Tab
now adopts the core order (forward at the first reachable core control, reverse
at the last). Focus is not taken on load, so mouse play shows no unrequested
focus ring.

### 3. The tactical-feed rail overlapped the status rail's real content

The status rail's authored box ends at y=410 but its content measured 514, so it
spilled past its own edge and sat under the tactical-feed rail pinned at y=424.
This is visible in the M05-001 pack `20260729T105741264Z-6aedeca9`
(`screenshots/02-tactical-booted.png`): the stance line and the core-cost line
are covered. The earlier visual review did not catch it.

The status content now scrolls inside its rail, so the panel reports the height
it actually occupies. Measured status-rail bottom returned to 410 and the feed
rail is disjoint at every supported canvas. Trade-off: the stance and core-cost
lines are now reached by scrolling rather than shown at once.

Compressing the rail's box was tried first and rejected — a shorter box does not
shorten its contents, so it produced a geometrically clean layout that rendered
worse.

### 4. A wrapped action dock overlapped the feed rail

The feed rail's bottom offset was a fixed `-112`, which assumed a single-row
dock. It is now computed from the dock's measured height.

## Model correction

`layout_metrics_for_width` covered width only. The layout and contrast model now
lives in `game/scripts/HudLayout.gd` as pure static functions, so headless checks
and the evidence emitter read exactly what the HUD applies, and
`metrics_for_viewport` adds the vertical dimension: measured status-rail bottom,
feed-rail top/bottom/height, dock top, and a `constrained` flag.

The action-dock base height was corrected from an estimated 98 to the measured
116.

## Supported boundary — narrowed, not widened

Sizes below are tactical-canvas sizes reported by the runtime, not browser
windows; the embedded launcher gives the runtime less room than the window.

| Browser window | Canvas | Feed-rail height | State |
|---|---|---:|---|
| 1920x1080 | 1172x659 | 93 | supported |
| 1600x900 | 1172x659 | 93 | supported |
| 1440x900 | 1112x626 | 60 | supported |
| 1366x768 | 1038x584 | 18 | supported |
| 1280x800 | 952x536 | -38 | constrained, declared unsupported |
| 1024x768 | 696x420 | -214 | constrained, declared unsupported |
| 768x1024 | 734x413 | -221 | constrained, declared unsupported |

Every supported canvas reports `event_rail_cramped`. The panels are disjoint and
the feed renders, but 18 pixels of tactical feed at 1366x768 is not a comfortable
surface. How much room the feed deserves is a design decision and is reported
rather than gated.

A wrapped 212-pixel dock makes every supported canvas constrained. Dock wrapping
was not observed at supported canvas widths in this run; if it occurs, the layout
reports the constraint instead of overlapping.

## Contrast

Seventeen core text and focus-outline pairs were computed against their own
panel, each panel composited over opaque white — the lightest backdrop a
tactical scene can place behind a translucent panel, and therefore the lowest
ratio the text can reach. All seventeen pass: lowest text case is the tactical
feed heading at 4.99:1 against a 4.5:1 minimum; the focus outline is 12.65:1
against a 3:1 minimum. Disabled text is excluded, as WCAG allows.

No colour was changed. The gate locks the current palette in place.

## Reduced motion

Camera transitions now pass through one boundary with a `motion_scale`. On the
Web export the host's `prefers-reduced-motion` is read once at camera
construction; a reduced-motion host applies each destination immediately instead
of tweening, and `focus_position` refreshes the camera transform so projected
observation coordinates are correct on the next publish rather than after the
0.35-second tween. Any other host keeps the authored motion.

Camera motion is presentation only: no mechanical result, AP cost, or published
observation target changes.

## Still open

- Compact HUD mode: the tactical feed is cramped at every supported canvas and
  absent below 952x536. A scrollable or collapsible dock, or a reduced status
  rail, would widen the supported set. Which information may be sacrificed is a
  design decision for the principal.
- Screen-reader and assistive-technology behavior: a canvas runtime exposes no
  accessibility tree. Not attempted, not claimed.
- Browser coverage beyond the resolved Chromium build.
- Operating-system text scaling and zoom.
- M03 canonical live cover/flank rationale scenario, unchanged by this module.
- Committed runtime and manifest parity, which belongs to an owner-approved M06.
