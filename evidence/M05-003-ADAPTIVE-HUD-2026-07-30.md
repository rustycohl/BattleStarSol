# M05-003 Adaptive HUD

## Authority

Principal decision, 2026-07-29: "ideally every hud element has variable
transparency, can 'scroll' or be slide back out of way, and is otherwise an
adaptive element."

This replaces the narrowed support boundary M05-B had to declare. Instead of
naming windows the HUD cannot serve, the HUD now adapts to them.

## The three axes

Every HUD surface — status rail, tactical feed, tutorial callout, action dock —
is adaptive along three independent axes:

| Axis | Behavior |
|---|---|
| Transparency | Continuous `0.15` to `1.0`, applied to the live control. Never fully invisible, so a faded surface can always be found again. A five-step cycle wraps, so repeated presses always return to full. |
| Slide | A surface parks off its own edge, leaving an 18-pixel handle on screen. Reversible. |
| Scroll | Content taller than its surface scrolls instead of spilling. The status rail and the action dock both scroll. |

Controls: **F2** selects the next surface, **F3** cycles its transparency, **F4**
slides it away or back. Each change is announced in the hint line, so the controls
are discoverable without a manual. Tab remains reserved for focus traversal.

## Adaptation

`HudLayout.adaptive_metrics` takes the player's intent and returns the arrangement
that actually fits. When the open arrangement cannot fit, surfaces park in a fixed,
documented order: the **tactical feed** first, because it is history and because
its own room is the constraint; then the **status rail**, once the dock rises high
enough to reach it.

The **action dock and the tutorial callout are never auto-parked.** Losing either
silently would remove the player's actions or their instructions.

Two rules keep the model honest:

- **Player intent is the only input.** Automatic parking is recomputed from
  scratch every pass, so an adaptation can never compound, and a surface the
  player never parked is restored the moment the room returns. An earlier version
  fed the previous pass's result back in, which let the metrics describe an
  arrangement the restore step then undid.
- **Rail extents are measured from the authored gutter plus the surface's own
  width, never from its current position.** A slid surface must report the room it
  would need when open, or the model and the applied layout disagree. Park offsets
  are derived from those same measurements inside the same pass; deriving them
  from a node's live size let a size that settled a frame later leave the handle a
  few pixels off the model's contract.

## A defect this work introduced and corrected

Wrapping the action dock in a `ScrollContainer` removed its intrinsic height: the
dock collapsed to a 16-pixel sliver and handed the layout a false measurement, so
short canvases appeared to fit when they did not, and keyboard traversal failed at
three viewports. The scroll container now holds the authored dock height and
scrolls only what exceeds it.

## Still open

- **Transparency and slide are keyboard-only.** There is no drag handle, no
  pointer affordance, and no on-screen control; F2/F3/F4 and the hint line are the
  whole interface. A pointer affordance is the obvious next increment.
- **Nothing persists.** Surface states reset each mission. Saving them to the local
  Commander profile would need a profile-schema change.
- **No animation.** A parked surface jumps rather than slides. Animating it should
  respect the reduced-motion preference already resolved in M05-B.
- The status rail's handle sits on the same left edge as the feed's, so at the
  smallest canvases two handles stack in a narrow column. Legible, not elegant.
- Screen-reader behavior, browser coverage beyond the resolved Chromium build, and
  OS text scaling remain untested, as in M05-B.
- Committed runtime and manifest promotion remains owner-gated M06 work.
